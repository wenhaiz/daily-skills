# Product Team Facilitation

Turn an ambiguous product question into a decision with explicit assumptions, role-specific reasoning, and a low-cost next step.

## Applicable scenarios

- Evaluate a product idea, feature scope, priority, or roadmap trade-off.
- Discuss activation, retention, positioning, launch, pricing, channel, or operational implications.
- Host a weekly product sync or reconcile disagreement across product, engineering, data, growth, and operations.
- Do not use for a single-domain request that only needs implementation help, copywriting, or a data query.

## Prepare the discussion

1. Restate the actual decision in plain language.
2. Read the smallest relevant project context: target users, product principles, current behavior, metrics, technical constraints, and prior decisions. Use the project's documentation system when present.
3. Separate known facts from assumptions. Ask one focused question only when its answer would materially change the recommendation.
4. Select roles; do not summon every role by default:
   - Product: user problem, priority, scope, success criterion.
   - Technical: system boundaries, complexity, risk, smallest maintainable option.
   - Data: testable question, evidence quality, minimum measurement plan.
   - Growth: message, audience, channel, and launch asset implications.
   - Operations: journey placement, repeat behavior, touchpoints, and ongoing cost.

## Facilitate and converge

- Keep each role in its lane; do not fabricate consensus, research, feedback, or metrics.
- Prefer the smallest reversible experiment when evidence is weak.
- State what should not be built now when scope needs protection.
- Route to real analytics tools or external research only when the decision requires live evidence.

## Required output

Use these sections:

1. **结论** — recommended decision and confidence.
2. **事实与假设** — distinguish evidence from uncertainty.
3. **角色观点** — selected roles only, with concrete reasoning.
4. **建议动作** — owner-neutral next step, minimum scope, and success signal.
5. **风险与待补信息** — what could change the decision.
6. **需要更新的 Docs** — project plans, stable facts, decisions, analytics catalog, or changelog that should be updated.
