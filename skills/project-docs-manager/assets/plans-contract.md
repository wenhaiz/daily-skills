# 可执行 Plan 合同

Plan 是持续维护的执行记录，不是开发开始后就失效的提案。不了解历史对话和仓库的新执行者，必须能够只依赖当前工作树和一份 Plan 理解目标、继续开发并验证结果。

## 选择 Plan 层级

范围清楚、实现路径明确、验证面较小的工作使用普通 Plan。

复杂功能、重要重构、跨模块改动、迁移、长时间任务、存在明显未知项、需要原型或分阶段验证时使用完整 ExecPlan。

两种 Plan 都必须：

- 自包含：重复继续工作所需的假设和仓库事实。
- 持续更新：进度、发现和决策变化时同步修改文档。
- 面向结果：说明完成后可以做到什么，以及如何观察结果。
- 决策完整：不把重要实现选择留给下一位执行者。
- 安全：涉及重复执行、中断、迁移或危险操作时说明恢复方式和边界。

## 所有 Plan 的必需内容

每份 Plan 必须包含：

- 状态和活文档声明
- 目的和可观察结果
- 新执行者需要的仓库上下文和名词说明
- 范围与范围外事项
- 实施步骤
- 区分已完成和剩余工作的带时间进度
- 附带简短证据的意外与发现
- 包含理由和日期的决策记录
- 带命令或可观察行为的验证与验收
- 结果与回顾
- ProductFact 和 Changelog 收口状态

完整 ExecPlan 固定维护 `Progress`、`Surprises & Discoveries`、`Decision Log` 和 `Outcomes & Retrospective` 四个区域；中文文档可以在中文标题后保留对应英文名称。

上下文和实施步骤优先使用完整句子说明。进度可以使用清单。文件使用仓库相对路径；命令要写明工作目录。

## 完整 ExecPlan 的附加内容

完整 ExecPlan 还必须包含：

- 足够仓库新手定位代码的上下文与导航
- 每一步都能独立验证结果的叙述式里程碑
- 准确命令、预期输出和判断方式
- 明确模块、服务、类型或函数签名的接口与依赖
- 可重复、中断、危险或迁移步骤的幂等与恢复说明
- 只保留关键输出、差异或日志的证据记录

可行性存在明显未知项时，先增加可以独立验证的原型里程碑，同时写清保留、放弃和清理原型的条件。

## 生成流程

1. 搜索活动和已归档 Plan，避免为同一任务创建重复文档。
2. 同一任务已有活动 Plan 时继续维护原文档。
3. 优先使用仓库命名约定；没有约定时使用 `yyyy-MM-dd-<kebab-title>.md`。
4. 从 [Plan 模板](../0-ProductFact/90-templates/plan-template.md) 开始，检查真实代码、测试、配置和仓库规则。
5. 在 Plan 内解决重要选择并说明理由；把执行所需的外部知识改写成自包含说明。
6. 实施开始时将状态改为 `active`。

## 实施流程

编辑代码前，完整阅读 Plan 和本合同，并先确认 Plan 与当前工作树一致。之后在用户授权范围内继续下一个未完成里程碑。

每个停顿点都要：

- 给进度增加时间
- 将部分完成的工作拆成明确的已完成和剩余内容
- 记录意外行为和简短证据
- 记录改变或澄清方案的决策
- 同步更新受影响章节，保持整份文档一致

验收必须证明有用的行为。用户功能需要说明如何操作及应该看到什么；内部改动应尽量提供改动前失败、改动后通过的可复现测试或场景。除非编译本身就是目标，否则只编译通过不算完整验收。

下一里程碑已经得到授权且安全时，不要只为询问下一步而暂停。这不代表可以执行危险操作、对外发布、提交代码或扩展用户授权范围。

## 完成与归档

重要里程碑和整个 Plan 完成时，更新「结果与回顾」，记录实际完成内容、剩余事项和经验。验证区域写实际结果，不保留尚未执行的命令作为完成证据。

必要验证通过并将稳定行为同步到 ProductFact 后，才能把状态改为 `completed`。有意义的交付同步写入 Changelog，再保留原文件名移到 `archived/`，并更新旧路径引用。
